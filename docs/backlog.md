## 💡 需求与优化事项池

### 1. 工作区状态同步机制演进（解决盲轮询耗电与延迟）

- **状态**：`[待定 / 需服务端配合]`
- **提出时间**：2026-10-18
- **当前现状**：
  - 前端 `src/workspace/useWorkspaceSnapshot.ts` 目前以 5 秒固定间隔向服务端轮询 `GET /api/agent` 与 `GET /api/actions/pending`。
  - 数据在 98% 的时间无变动，持续请求导致移动端射频芯片持续高功耗工作、浪费网络流量；
  - 当用户把 App 切入后台（锁屏或切到其他 App）时，面临两难困境：若停掉轮询，后台任务完成或生成新审批时手机端无法及时获知；若不停轮询，极易被 iOS/Android 系统判定为异常后台耗电而杀进程。
- **为什么纯前端难以完美解决**：
  - 纯前端最多只能在切后台（`AppState !== 'active'`）时降频或暂停定时器，但无法在“用户锁屏期间后台任务完成”时实现被动及时感知。必须服务端具备按需主动触达或轻量分发能力。
- **候选方案对比**：
  - **方案 A（全局轻量 SSE `/api/events`）[高性价比推荐]**：
    - **机制**：服务端提供一个轻量事件长连接，仅在工作区变动（任务状态迁移、新文件审批下发、目标更新）时推送极简事件（如 `{ event: "task_updated", id: "xxx" }`）。
    - **收益**：客户端彻底废除 5 秒定时器，改为“有事件才拉取快照（On-Demand）”，平时零流量开销。
  - **方案 B（HTTP 缓存头 ETag / 304 Not Modified）[最小改造]**：
    - **机制**：服务端在 `/api/agent` 支持 `If-None-Match: <revision>`。无变动时直接返回 `304 Not Modified`（0 字节 Body）。
    - **收益**：减少 JSON 序列化与数据传输，但客户端仍需周期性发起网络请求，未解决定时器唤醒耗电。
  - **方案 C（系统级远程推送 FCM / APNs）[针对切后台终极形态]**：
    - **机制**：手机在前台时走 SSE 实时同步；切到后台或杀进程后断开长连接，任务完成由服务端发送原生推送唤醒系统通知栏。
    - **收益**：真正符合主流移动端体验，但需要依赖推送网关和设备 Token 注册。
- **当前结论与备忘**：
  - 先在此建档备忘；待后续服务端架构规划明确后，再与服务端统一对齐接口契约与推送协议。
